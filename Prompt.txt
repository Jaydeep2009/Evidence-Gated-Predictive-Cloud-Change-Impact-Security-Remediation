============================================================
1. PROJECT OBJECTIVE
============================================================

The project is a research-oriented, open-source, locally reproducible system that predicts the security and operational impact of proposed cloud/infrastructure security changes BEFORE they are applied.

The main problem is:

Cloud/security changes can improve security but can unintentionally break applications or services.

Dependency information is distributed across:
1. Infrastructure configuration
2. Application/source-code information
3. Runtime behavior/telemetry

A security change should therefore not be judged only from infrastructure configuration.

The system should combine:

Infrastructure Evidence
+
Application Evidence
+
Runtime Evidence

to construct a Unified Evidence/Dependency Graph and use that evidence to predict:

- Security impact
- Operational risk
- Affected components
- Confidence
- Supporting evidence/reasoning

The system must also be able to recognize when there is NOT enough evidence.

Therefore, the decision layer must support:

SAFE
RISKY
INSUFFICIENT EVIDENCE

When a change is risky, the system should attempt a minimal safe remediation when appropriate, then perform controlled verification and compare:

Prediction vs Actual Runtime Result.

The overall research story is:

Proposed Cloud/Security Change
→ Change Parser
→ Infrastructure Evidence
+ Application Evidence
+ Runtime Evidence
→ Unified Evidence/Dependency Graph
→ Impact Prediction
→ Security Impact
+ Operational Risk
+ Affected Components
+ Confidence
→ Evidence Gate
→ SAFE / RISKY / INSUFFICIENT EVIDENCE
→ Minimal Safe Remediation when appropriate
→ Controlled Verification
→ Actual Runtime Result
→ Prediction vs Reality
→ Final Decision Report

============================================================
6. IMPORTANT EVIDENCE PRINCIPLE
============================================================

One of the central research principles is:

“Absence of observed runtime usage does NOT automatically mean absence of dependency.”

For example:

If PostgreSQL was not observed during a short runtime test, the system must not automatically conclude:

Backend does not depend on PostgreSQL.

Possible explanations:

- functionality was not exercised
- insufficient workload
- telemetry was incomplete
- dependency is conditional
- evidence collection failed

Therefore:

Incomplete/conflicting evidence should reduce confidence.

The system should be able to say:

INSUFFICIENT EVIDENCE

rather than making an unsafe high-confidence decision.

16. SECURITY ANALYSIS
============================================================

Security analysis can consider:

- privilege reduction/increase
- attack surface
- access control
- least privilege
- isolation
- lateral movement
- unauthorized communication
- network exposure
- overly permissive rules
- denied required communication

For Kubernetes NetworkPolicy:

Consider:

- ingress
- egress
- podSelector
- namespaceSelector
- ports
- policyTypes
- allowed/denied communication
- isolation

Important principle:

Security improvement can create operational risk.

The system must evaluate BOTH.

Do not treat:

“more restrictive = always better.”

Example:

Blocking all backend→database traffic may improve isolation but break the application.


============================================================
17. EVIDENCE GATE
============================================================

The gate is a core research component.

Possible outputs:

SAFE

RISKY

INSUFFICIENT EVIDENCE

Conceptually:

IF:
evidence is strong
AND predicted impact is low
AND no important dependency is affected
→ SAFE

IF:
evidence is strong
AND important dependency/security trade-off is detected
→ RISKY

IF:
evidence is incomplete/conflicting
AND confidence is insufficient
→ INSUFFICIENT EVIDENCE

The system must not force a binary safe/unsafe answer when evidence is insufficient.


============================================================
18. MINIMAL SAFE REMEDIATION
============================================================

When a proposed change is risky, remediation should aim to:

- achieve the intended security goal
- preserve necessary application functionality
- follow least privilege
- minimize unnecessary permissions/communication
- avoid broad allow rules
- avoid simply undoing the security change

Example:

Instead of:

DENY everything

or:

ALLOW everything

generate a narrow rule that permits only the required Backend→Database communication while maintaining appropriate restrictions.

Remediation must be validated.

Scanner success alone is not enough to prove semantic correctness.


============================================================
19. CONTROLLED VERIFICATION
============================================================

Verification must occur in a controlled local environment.

Process:

1. Start known baseline system.
2. Collect baseline evidence.
3. Propose change.
4. Predict impact.
5. Apply change.
6. Run predefined workload.
7. Collect telemetry/logs/metrics.
8. Determine actual result.
9. Compare prediction vs reality.
10. Store result.

The project should produce reproducible experiment records.

40. IMPORTANT EDGE CASES
============================================================

The system must consider:

1. Dependency exists in code but was not exercised at runtime.

2. Runtime dependency exists but infrastructure evidence is incomplete.

3. Infrastructure configuration says communication is allowed but runtime shows no traffic.

4. Different evidence sources conflict.

5. Telemetry is missing.

6. Service is conditionally dependent on another service.

7. Security change affects multiple components.

8. Security improves while availability decreases.

9. A broad deny rule blocks unrelated functionality.

10. A remediation passes a scanner but is semantically wrong.

11. Multiple services share a database.

12. NetworkPolicy selectors match more pods than expected.

13. Change affects ingress and egress differently.

14. IAM permission is removed but actual usage is unknown.

15. Runtime evidence is stale.

16. Evidence confidence should depend on source and quality.

17. The system should abstain when confidence is insufficient.

45. FINAL PROJECT STORY FOR PRESENTATION
============================================================

The simplest way to explain the project is:

“Cloud security changes are not isolated from application behavior. A security rule that looks correct from the infrastructure perspective can unintentionally break a service dependency. Our project therefore combines infrastructure configuration, application dependencies, and runtime observations into a unified evidence graph. Before applying a proposed security change, the system predicts its security and operational impact and reports the affected components along with confidence. If the evidence is insufficient, the system abstains instead of making an unsupported decision. If the change is risky, it can attempt a minimal remediation. Finally, the proposed change is executed in a controlled local Kubernetes environment and the predicted result is compared with the actual runtime behavior. This allows us to experimentally evaluate whether combining heterogeneous evidence improves cloud-security change-impact prediction.”

That is the core project story.
